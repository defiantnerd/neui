## Deferred Issues

- **UI-zoom follow-ups** (`NEUI_ATTR_UI_SCALE` ships on the xpl host - see `docs/attributes.md`): **iOS and the null platform gate it OFF** via `platform_supports_ui_scale()` (iOS takes touch coords raw from `locationInView:` and does not scale view sizing, so scaling paint alone would hit-test in a different space than it draws - inert is better than half-working); no xpl platform tracks user window MOVES back into `wd.x/y`, which is why the zoom re-apply passes `NEUI_WINDOW_POS_KEEP` rather than the stored position; scroll/wheel DELTAS are not zoom-divided (zoomed content scrolls `zoom`x faster than the gesture - feel, not correctness); DnD drop coordinates are not zoom-divided on win32 or Linux; `NEUI_ATTR_PAINT_DEVICE_PIXELS` undoes the ZOOM only, not the DPI, so one unit is still `1/backing_scale` of a physical pixel on HiDPI; Linux multiplies window POSITION by the zoom while win32/macOS do not (self-consistent per platform, but a cross-platform placement difference); `set_int(NEUI_ATTR_UI_SCALE, 2)` silently no-ops (the side effects hang off `set_float`, per the typed-attr convention).

- **Timer follow-ups** (`NEUI_API_TIMER` ships - see `<neui/d/timer.h>`): no one-shot timers (a client removes the timer from its own handler, which is tested and safe); no sub-millisecond or vsync-locked cadence (the tick is a plain OS timer, and `NEUI_TIMER_MIN_INTERVAL_MS` = 4 is the floor); the interval is a minimum with no drift compensation, since a late tick deliberately fires once rather than catching up; the null platform accepts timers and never fires them (it has no loop to hang a tick off).

- **Deduplication non-goals** (a 2026-06 dedup campaign consolidated the asset managers, draw_asset thunks, DnD dispatch/seam/helpers, macOS window helpers and backend colour/alpha math into `hosts/shared/` + `backends/shared/`; these were deliberately left per-host/per-backend - do not "unify" them): DnD hit-test walkers (xpl virtual `hit_test` vs native on-the-fly coord accumulation - different contracts), the two macOS window delegates' close logic (native drives sheet `endSheet:` in `windowShouldClose:`, xpl tears down the render ctx in `windowWillClose:`), backend transform/clip stacks (CG `SaveGState` saves clip+CTM atomically), font-cache containers (D2D struct-keyed wstring vs CG string key), the null backend's explicit no-op vtable (documents the interface), example scaffolding.
- **KNOB not a keyboard tab-stop on macOS** - the NSView refuses first responder. Needs focusable + arrow-key value handling.
- **macOS Tab participation follows the system Full-Keyboard-Access setting** - traversal *order* matches win32, but *which* control types Tab visits beyond text fields / lists is OS policy. Hand-roll Tab for fully deterministic traversal.
- **Tier B focus parity** (xpl proxy HWND per widget for UIAutomation; NSAccessibility seam on macOS).
- **Image clipboard / DnD** - `text/plain`, `text/html`, `text/uri-list`, arbitrary MIMEs, and `image/png` (`NEUI_MIME_PNG`) are wired on all three hosts. Win32: `image/png` is published as `CF_DIBV5` (PNG bytes decoded via WIC into a `BITMAPV5HEADER` + 32bpp BGRA pixel block) alongside the registered MIME, so Paint / Explorer / Outlook see the image; reverse path re-encodes a `CF_DIBV5` / `CF_DIB` drop back to `image/png` bytes via WIC. macOS: `image/png` stamps `NSPasteboardTypePNG` (same bytes - PNG is the native macOS bitmap format). `image/tiff` not yet wired (the converter helpers live in `hosts/shared/win32/clipboard_format_png_win32.h`; TIFF would follow the same shape).
- **DnD drag-source extensions** - drag-source API, the `DRAG_SOURCE` behavior-asset handler kind, the custom drag-preview image (`begin_drag_with_preview`; `NSImage` / `IDragSourceHelper`), per-drag result feedback (`DRAG_SOURCE` `result_attr` prop - runtime writes the negotiated `NEUI_DND_ACTION_*` as int + fires `ATTR_CHANGED` + invalidate after `begin_drag` returns), and the generic lazy-provider callback (`clipboard->item_set_format_callback` - bytes produced on demand by a `neui_data_provider_t`; Win32 `DataObjectImpl::GetData` and macOS `NSPasteboardItemDataProvider` defer encoding for arbitrary MIMEs until the receiver actually requests them; built-in MIMEs and clipboard write materialise eagerly at snapshot/write time) all ship on all three hosts; deferred follow-ups: file-promise interop (`CFSTR_FILECONTENTS` + `CFSTR_FILEDESCRIPTOR` for Explorer / Outlook; `NSFilePromiseProvider` for Finder - separate from the generic provider in that the OS wants a path / IStream specifically), true deferred-render on clipboard write via `WM_RENDERFORMAT` (Win32) and `NSPasteboardItem` promise-of-promise (macOS).
- **Per-child-widget DnD on macOS native** - resolved: the framework hit-tests the widget tree (`find_drop_target_in_frame_macos`), matching win32 native + xpl. `NEUINativeContentView` is still the only `<NSDraggingDestination>` (child painted views don't register their own, exactly like child HWNDs on win32); a per-painted-view native opt-in remains possible but isn't needed for behavioral parity.
- **macOS clipboard change-notification** - `NSPasteboard.changeCount` polling is not wired; the API has no `onchange` event anyway, clients poll on demand.
- **Multi-level redo on win32** - `NEUI_CMD_REDO` maps to `EM_UNDO` (single-level toggle); macOS native + xpl are multi-level.
- **Multi-session palette** - `active_palette_override_ptr` is process-wide (last-set-wins).
- **SVG filter primitives** beyond `feFlood` / `feColorMatrix` / `feOffset` / `feGaussianBlur` / `feComposite` / `feBlend` / `feMerge`: `feMorphology` (the blocker for an outline/stroke convenience), `feComponentTransfer`, `feTile`, `feImage`, `feTurbulence`, `feDisplacementMap`, `feConvolveMatrix`, lighting. Also: linearRGB colour-interpolation (sRGB only today, per the designer's `color-interpolation-filters="sRGB"`), `feComposite operator="out"` semantics for *semi-transparent* (vs opaque) shapes, and an SVG `<filter>` *parser* feeding the graph (the engine is parser-agnostic; parser location - in-core vs helper lib - is an open decision). Filters are CPU/bake-time on a SURFACE by design; per-frame GPU filtering would be a separate backend-native layer.
- **Compound layer kinds** beyond `text` / `asset` / `rect` / `path` / `qr` / `group`: template format specs (`{key:.2f}`); SVG-mini string form for `set_path`. (Cubic/quadratic bezier on PATH now ship - `NEUI_PATH_CMD_CUBIC_TO`/`_QUAD_TO`, `neui_path_cmd_t.args` widened to `[6]`, **full rebuild required** like the `AssetEntry` note. The `group` container layer now ships too - `NEUI_COMPOUND_LAYER_GROUP` + `add_child_layer`, see the Compound drawables section.)
- **Behavior detent / plateau modifier** - per-handler "sticky values" that resist near specific points (distinct from `steps`); behavior pen pressure / tilt (pen surfaces as mouse); `cursor` prop no-op. (**Wheel modifier-fine now SHIPS**: `neui_event_wheel_t` carries a `NEUI_MK_*` `buttonmap` - populated on win32 native + xpl, macOS native + xpl, linux xpl; iOS synthesises the wheel from touch pans and reports 0, which is accurate there. Two rules make it safe, both on the WHEEL branch in `hosts/shared/behavior_runtime.h`: a horizontal notch **with** Shift is the platform layer's flipped-and-negated vertical notch and gets un-negated - the Shift->horizontal flip stays in the platform layer by design, so a consumer with no horizontal axis undoes it - while a genuine tilt-wheel horizontal notch is untouched; and with `steps` detents a notch advances exactly one detent and fine is ignored, matching the native KNOB and avoiding the round-to-nearest starvation a sub-quantum fine change would hit. Tier-1 covered in `tests/test_behavior.cpp`.)
- **GRID sort follow-ups** - STRING kind is byte-level `strcmp` (locale-aware compare deferred); no per-column custom comparator callback (clients pre-format or pick STRING / INT / FLOAT / NATURAL); no built-in DATE / TIME kind.
- **UI zoom (`NEUI_ATTR_UI_SCALE`) follow-ups** - baked SURFACEs and CPU filter results are rasterised once at a client-chosen scale, so a zoomed frame samples them up (softer); re-baking at the new scale is the client's call, exactly as for a DPI change, and there is no API to rescale an existing surface. `@2x`/`@3x` file assets are picked once at load from `best_asset_scale` and are not re-picked when the zoom changes. The zoom is per-frame (there is no `set_session_float`, so no session-wide knob). **Zoom is an xpl-host feature by design**: the native win32 / macOS hosts ignore the attr entirely (they parent real OS child controls, so there is no single surface to apply one CTM scale to, and scaling an HWND / NSView tree is the OS's job via DPI - not ours). A client that wants zoom selects `neui.host.crossplatform`, exactly as for `NEUI_API_EMBED` and `NEUI_API_TIMER`. See the **capability query** entry below for how a client is *supposed* to discover this. Drag-and-drop drop coordinates are not zoom-divided on any platform (each of the three has its own conversion outside the mouse seam - win32 `dnd_target_win32.h::screen_to_client`, Linux `DropTarget::dpi`), so a drop lands at 1/zoom of the cursor while zoomed; macOS *is* covered (it shares `frameZoom`). Linux input/sizing is wired but unverified (no Linux machine in the loop).
- **Cursor (`NEUI_ATTR_CURSOR`) follow-ups** - **xpl host only**: the native win32 / macOS hosts don't resolve the attr (their widgets are real OS controls that manage their own cursors), same shape as `NEUI_ATTR_UI_SCALE`. Relatedly, the *native* win32 host's GRID still re-sets its column-resize cursor from `WM_MOUSEMOVE` with no `WM_SETCURSOR` handler, so it keeps the per-move flicker that the xpl host's new handler fixes; harmless but unfixed, and it would want the same treatment if the native host ever grew cursor support.
  - **Applies only to hit-testable widgets.** Resolution starts from the hovered widget, and `widget_at` only returns widgets with `emit_events && enabled && !input_transparent`. So the attr is **inert on a LABEL, an IMAGE, a non-scrolling SECTION's bare background, or anything `input_transparent`** - the pointer is logically interacting with whatever lies beneath, so that widget's cursor wins. This is consistent with `input_transparent`'s documented meaning, and inheritance still reaches *through* a non-hit-testing widget to its interactive children. Making it apply to non-interactive widgets would need a cursor-only hit-test walk (ignoring `emit_events`) plus a tracked pointer position, since `refresh_cursor` is driven by hover transitions rather than coordinates.
  - **Per-platform shape gaps.** Fallbacks go to the nearest neighbour, never to an arrow-by-default. **macOS**: the diagonals are public from macOS 15 (`+frameResizeCursorFromPosition:inDirections:`, used when SDK + runtime both have it), a guarded private selector before that, and a same-axis double arrow as the last resort; `move` and `help` have no public equivalent at any version (private selector, else `openHandCursor` / arrow); `wait` / `progress` **cannot be honoured at all** - macOS has no app-settable busy cursor, the beachball is the window server's response to an unresponsive app, so a Mac client should *draw* progress. Also: `+resizeLeftRightCursor` / `+resizeUpDownCursor` (still used for EW / NS) are `API_TO_BE_DEPRECATED` in the macOS 15 SDK in favour of `+columnResizeCursor` / `+rowResizeCursor`; migrating is queued but deliberately not done yet, since it would change the existing GRID column-divider appearance. **win32** has no stock open/closed hand (both -> `IDC_HAND`). **X11** covers every shape from the cursor font but has no closed-hand or progress glyph (-> `XC_fleur` / `XC_watch`), and its diagonals are corner glyphs rather than double arrows.
  - **Other deferrals**: no *custom* (client-image) cursor and no hot-spot control; the behavior asset's per-handler `cursor` prop is still a no-op (the infrastructure it was blocked on now exists - it needs a per-handler hit-region hover track plus a new `BehaviorDispatchCtx` callback across all five platforms); cursor state is process-wide (`s_cursor_kind` / `g_cursor_kind`), correct for one pointer but would need per-seat state for multi-pointer X11; and the per-`Display` X11 cursor cache for the main display is a deliberate process-lifetime cache (one `XCreateFontCursor` per shape, freed by the server at exit) rather than a leak.

- **Relative pointer (`NEUI_API_POINTER`) follow-ups** - **xpl host only**, like `_TIMER` / `_EMBED`; `begin_relative` returns false on iOS and the null platform (no cursor to pin), so a touch build degrades to ordinary bounded drags. **Opt-in by design**: the built-in KNOB / SLIDER and the behavior asset's `DRAG_*` handlers do NOT enter relative mode themselves - hiding the cursor is a visible change, and a client that draws a readout at the pointer, or that simply prefers bounded drags, should not have it forced on. A client brackets it from the widget's own DOWN / UP events. Deferred: no *per-widget* opt-in attribute (it would need one begin/end per drag inside the widget implementations, plus a decision about what a behavior asset's `DRAG_*` should do by default); the mode is process-wide single-instance (one pointer, so one drag - a multi-pointer X11 seat would need per-seat state); win32 and X11 use the warp-back model, so they burn one extra motion event per move (the echo) where macOS's `CGAssociateMouseAndMouseCursorPosition(false)` needs none; and **sub-pixel accumulation is Tier-1 tested only** - a synthesized `NSEvent` cannot carry a fractional delta (`+[NSEvent eventWithCGEvent:]` quantises `kCGMouseEventDelta*` to an integer: 2.5 -> 2.0, 0.3 -> 0.0), so the macOS harness proves exact integer accumulation and leaves the float path to `tests/test_relative_pointer.cpp`. Real trackpad events *are* fractional, which is why the accumulator is float rather than int. Further: on **Linux** the delta is measured event-to-event rather than from the anchor (an anchor-relative delta double-counts whenever more than one `MotionNotify` is queued before the asynchronous `XWarpPointer` lands, which a repaint-per-move drag makes routine) - win32 is immune because `GetCursorPos`/`SetCursorPos` are synchronous, but the Linux path is unverified on real hardware; and on **macOS** the restore warps before re-associating so the ~250 ms local-events suppression interval does not leave the pointer feeling dead after every drag, which is reasoned from the documented suppression behaviour rather than measured here.

- **No capability-query API** - a client can feature-detect a whole *interface* (`get_interface` returns null: `NEUI_API_EMBED`, `NEUI_API_TIMER`, `NEUI_API_FILTER` all rely on this), but there is **no way to ask whether a given host supports a given feature *within* an interface it does expose**. `NEUI_ATTR_UI_SCALE` is the motivating case: it is a plain `NEUI_ATTR_*` key on `NEUI_API_ATTRS`, which every host exposes, and the two native hosts silently ignore it - a client sets it, `get_float` reads back what it wrote, and nothing zooms, with no error and nothing to test. The same shape applies to any attr a host chooses not to honour (`NEUI_ATTR_LINE_WRAP` on a native MULTILINE, `NEUI_ATTR_PAINT_DEVICE_PIXELS` off the xpl host, `NEUI_ATTR_FOLLOW_SYSTEM_THEME` without D-Bus on Linux) and to per-platform sub-features behind a *present* interface (`NEUI_API_NOTIFY::message_box` everywhere vs. a native file dialog only where one exists). Internally the host already knows: `platform_supports_ui_scale()`, `platform_menubar_in_frame()`, `NEUI_HAS_XI2` / `NEUI_HAS_DBUS` are exactly these answers, just not reachable from a client. **Wanted**: a small `NEUI_API_CAPS` (`bool supports(session, const char* feature_key)`, keyed by the same `NEUI_ATTR_*` / `NEUI_API_*` / feature strings, plus an enumerate for tooling) so a client can grey out a zoom menu on a native host instead of shipping a control that does nothing. Until it exists, the rule is: **a host's identity string is the capability check** - select `neui.host.crossplatform` explicitly when you need zoom, embedding, or timers, and treat the doc tables in `docs/attributes.md` as the contract.

- **Embedded PLUGWINDOW (`NEUI_API_EMBED`) follow-ups** - the embedded frame does not auto-track parent resizes (the plugin adapter drives size explicitly via `widgets->set_size` after host resize negotiation - correct for plugin formats, where size is negotiated, but a free-following mode could add an autoresize/frame-observer opt-in); win32 embedded frames don't receive `WM_DPICHANGED` (it goes to the DAW's top-level - a monitor change mid-session keeps the old scale until recreate); embedded keyboard focus is click-to-focus only - it works (win32 `SetFocus` on `WM_LBUTTONDOWN` for a `WS_CHILD` frame, macOS `makeFirstResponder:` in `NEUIView mouseDown:`, both skipped for standalone frames which the OS focuses itself) but the frame does not participate in the DAW's own tab loop; the native win32/macOS hosts do not implement `NEUI_API_EMBED` (xpl host only - by design, plugin builds select `neui.host.crossplatform`).


- **Rich popup menu (`NEUI_W_POPUPMENU` / `popup_tree_menu`) follow-ups** - **xpl host only**: the native win32 / macOS / iOS hosts hold an explicit `nullptr` in the vtable slot (each with a comment naming what it would need - `TrackPopupMenuEx`, `-[NSMenu popUpMenuPositioningItem:atLocation:inView:]`, `UIMenu`). They would also need the item model those hosts deliberately don't keep (their menus live in `HMENU` / `NSMenu` directly), so this is a real port, not plumbing. **iOS xpl is explicitly unsupported**: `platform_supports_tree_popup()` returns false there and `show_tree_popup` refuses, because `paint_frame` paints the cascade platform-independently and the iOS touch path has no tree-popup hit-test - so wiring paint without input would put up a menu whose taps fall through to the widgets underneath with nothing able to dismiss it (no Esc). A `UIMenu` / `UIContextMenuInteraction` bridge is the right answer for iOS, not a port of the pointer-shaped hit-testing. Also: **only macOS is verified at runtime** - win32 and Linux are wired at the same call sites as the existing `_popup_active` overlay (press / move / release / Esc plus the release swallow) but neither can be compiled on the machine in the loop, and Linux has no native host to fall back to. **Keyboard navigation is Esc-only**: the in-frame menubar's arrow / Enter / Home / End walk (`handle_menubar_key`) is not shared with the popup, so a popup is mouse-driven apart from dismissal; wiring it would mean generalising `handle_menubar_key` over the same `_menu_path` the popup already borrows. A popup's per-item **shortcut is a label, never an accelerator** - the widget is deliberately absent from `Session::_menubars`, so neither `try_menubar_accel` nor `try_translate_accel` can see it; bind the real accelerator on the menu bar. `set_menu_cmd` with a **USER-range** command on a popup row does nothing (built-ins route through `invoke_focused_command`; user commands are the client's job from `ITEM_SELECTED`). Only **one** menu cascade can be open at a time process-wide per session (the popup borrows `_menu_path` / `_menu_hover_item` from the menubar), which matches the OS menus it mirrors but means opening a popup closes an open menubar dropdown. No scrolling for a menu taller than the frame (it clamps, so the overflowing tail is unreachable) and no tear-off / multi-column layout - the wheel is *absorbed* while a popup is open on all three platforms (so a SECTION / GRID underneath cannot scroll away beneath the visible menu) rather than scrolling the menu. **Right-click inside an open popup picks the row under the cursor** (matching `NSMenu`) rather than dismissing, which differs from native win32 menus.

- **File dialog (`NEUI_API_NOTIFY::open_file` / `save_file`) follow-ups** - **only macOS is verified at runtime.** `tests/file_dialog_smoke_macos.mm` drives real modal panels on both macOS hosts (38 checks), and `tests/test_file_dialog_model.cpp` covers the portable half everywhere (26 cases). The win32 `IFileDialog` path and the entire Linux path - portal *and* drawn browser, ~450 lines of X11 + Cairo + D-Bus - are written against the same seams as the shipping message box but **cannot be compiled on the machine in the loop** (no MSVC, and no X11 / Cairo / D-Bus / pkg-config on the Mac). That is inspection, not a tested claim. The Linux design deliberately de-risks its own untestable part: the portal is best-effort and *any* failure falls through to the drawn browser, so a D-Bus marshalling bug degrades to a working dialog rather than breaking the feature.
  - **Async / iOS.** Both slots return `-1` on iOS and the null platform. `UIDocumentPickerViewController` is presented, not run modally, and unlike `message_box` there is no useful "pending" sentinel - the return value *is* the path list. The real fix is a **completion event** (`NEUI_EVENT_*` carrying the picked paths, or a per-call callback invoked later), which would also retire the `NEUI_MB_IOS_PENDING` divergence in `message_box`; both are blocked on the same thing and should land together. Note the blocking contract is fine for the desktop plugin case the API was added for (patch load / save from a DAW UI thread).
  - **Flags a platform cannot honour**, all no-ops rather than errors: `NEUI_FD_NO_OVERWRITE_PROMPT` on macOS (NSSavePanel always confirms and offers no switch) **and on the Linux portal path** (the FileChooser interface marshals no such option - the backend decides), so on both the prompt cannot be turned off; win32 `IFileSaveDialog` and the drawn browser do honour it. All divergences point the same way - an extra confirmation, never a silent clobber. `NEUI_FD_SHOW_HIDDEN` is a no-op on win32 (a global Explorer setting, no per-dialog switch) and a hint on macOS / portal, where the user's own setting may win.
  - **Filter expressiveness is not uniform.** A wildcard *inside* an extension (`*.p?g`) works on win32 (the shell matches it) and in the drawn browser (the portable matcher), but is **dropped on macOS** - `allowedContentTypes`/`UTType` is an extension set, and the deprecated `allowedFileTypes` is not an option in a build that treats deprecation warnings as failures. Such a filter widens to "everything" on macOS. Matching is ASCII case-insensitive everywhere by deliberate choice; a case-*sensitive* filter is not expressible.
  - **macOS 11 floor for filtering.** `UTType` + `setAllowedContentTypes:` are macOS 11+, guarded with `@available`; on 10.15 and earlier the panel runs but does not filter by type. Fixing that properly means the deprecated setter, so it is left alone.
  - **No dialog state is remembered by neui.** There is no "last directory" memory of our own: win32 and macOS inherit the OS's per-app recall (which is why `SetFolder` is used rather than `SetDefaultFolder` - an explicit `initial_dir` must win), the portal has its own, and the drawn browser starts from `initial_dir` or `$HOME` every time. A client that wants stickiness stores the directory itself.
  - **Drawn-browser gaps** (it is the no-desktop fallback, not a file manager): fixed 560x420 with no resize and no layout pass; no scrollbar *thumb* to drag (wheel / arrows / PageUp-Down only); no type-ahead, no sorting controls, no rename / new-folder / delete; the filter chip *cycles* rather than dropping a list; no icons (a trailing `/` is the whole folder affordance); no symlink-loop guard beyond `readdir` (a cycle is navigable but harmless); no file sizes or dates. `NEUI_FD_MULTISELECT` is Ctrl-click only (no Shift-range). The overwrite prompt *is* implemented (an in-window overlay with a scrim, defaulting to the non-destructive answer on both Enter and Esc, absorbing the wheel like the popup-menu gate) rather than left as a silent clobber, but it is a plain "already exists, replace?" - no size/date comparison and no per-file detail.
  - **Portal specifics.** A ~5-minute timeout exists only so a portal that dies mid-dialog cannot hang the app; hitting it reports `unavailable` and runs the drawn browser, which on a slow chooser would mean two dialogs. Portal `response == 2` ("other reason") reports *cancelled* rather than falling through - a judgement call, not a clear win: it assumes a portal far enough along to answer had already shown its chooser, and the spec does not guarantee that, so a backend failing *before* display leaves the user with no dialog and the client with a "cancelled" nobody performed. Chosen because the alternative failure (a second dialog stacked on a dismissed first) is the more visible one. Non-`file://` URIs (a portal handing back a remote document) are dropped, and an otherwise-successful pick that yields no usable path is reported as a cancel, since the client asked for paths. The documented save-completion rule is applied by `platform_file_dialog` after a portal save, because the portal has no `SetDefaultExtension` equivalent and a GTK-style backend does not append the active filter's extension itself.
