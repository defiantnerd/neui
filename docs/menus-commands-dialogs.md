## Routed commands

`NEUI_API_COMMANDS`. `neui_command_t`: `NONE/UNDO/REDO/CUT/COPY/PASTE/SELECT_ALL/DELETE`, `USER_BASE = 0x10000`. API: `invoke_focused(cmd) → bool`, `invoke(widget, cmd) → bool`. `tree->set_menu_cmd(menubar, item, cmd)` binds a menu item to a built-in command. On activation, `dispatch_menu_event` calls `invoke_focused_command(cmd)` first; if a focused widget consumes it, no `TREE_ITEM_ACTIVATED` fires (otherwise, or `cmd == 0` / `cmd >= USER_BASE`, the event reaches the client). `WidgetData::perform_command(cmd)` is the virtual seam; xpl text widgets route to `on_keydown` with a synthetic Ctrl+letter; macOS native (`invoke_focused_command_macos`) routes to the first responder via AppKit editing actions + `NSUndoManager` for UNDO/REDO.

Menu-item auto-disable on popup-open: built-in commands gray via `WidgetData::can_perform_command`; optional `neui_menu_client_t` (`NEUI_API_MENU_CLIENT`) `validate(token, menubar, item, cmd)` per non-separator item. Final `enabled = mi.enabled && (no built-in OR can_focused) && (no validate OR validate())`.

## Popup menus

**Two popup APIs.** `widgets->popup_menu(...)` is the flat one (below). `widgets->popup_tree_menu(session, anchor, x, y, menu)` is the tree-model one: build a `NEUI_W_POPUPMENU` widget with the generic tree API (`tree->add` under `tree_item_root` = the popup's rows, a child item = a cascading submenu, `"-"` = separator, plus `set_shortcut` / `set_checked` / `set_enabled` / `set_menu_cmd`), then show it. **Asynchronous** - returns at once and the pick arrives as `NEUI_EVENT_ITEM_SELECTED` on the POPUPMENU with `index` = the `neui_item_t` id; dismissal fires nothing. Async because a blocking popup needs a nested pump (which suppresses `NEUI_EVENT_TIMER`, see `<neui/d/timer.h>`) and re-enters the client from inside its own handler. A disabled item is the "section header" idiom. Custom widgets inside menus are out of scope by design. Implementation is almost entirely REUSE: `Session::show_tree_popup` / `paint_tree_popup` / `handle_tree_popup_click` / `_hover` in `hosts/crossplatform/host.cpp` drive the menubar's own `mb_build_columns` + the extracted `paint_menu_columns`, which differ for a popup in exactly one respect - an empty `band` means "level 0 opens at `(root_x, root_y)`" instead of under a band item. So cascades to arbitrary depth, right/bottom clamping, submenu left-flip, checkmark gutters, shortcut columns and `NEUI_API_MENU_CLIENT::validate` all come for free. `NEUI_W_POPUPMENU` is a distinct type from `NEUI_W_MENUBAR` (sharing `MenubarWidget` wholesale) precisely so it is never mistaken for a frame's menu band - a MENUBAR child of a frame reserves an in-frame band on hosts that draw their own. **xpl host only**: the native win32 / macOS / iOS hosts leave the slot an explicit `nullptr` (null-check it, per the vtable-append rule). Verify: `tests/popup_tree_smoke_macos.mm` (`neui_popup_tree_smoke_macos`, 14 checks, needs a GUI session).


`widgets->popup_menu(session, anchor, x, y, items[])` - blocking; items NULL-terminated UTF-8 (`"-"` = separator); returns 1-based pick or 0. Win32: `TrackPopupMenuEx` + `TPM_RETURNCMD`. macOS: `run_popup_menu_macos` (`NSMenu`, per-item target; separators consume an index). xpl: session overlay + nested pump via `platform_run_modal_until(bool*)`. Used by the KNOB right-click "Reset to default" menu (`NEUI_EVENT_MOUSE_RBUTTON_DOWN`).

## Modal dialogs

`widgets->show(sess, dialog)` blocks the calling thread until the modal DIALOG (`NEUI_ATTR_MODAL=1`, default) is destroyed. All three hosts run a nested OS event pump while modal: xpl reuses the popup-menu primitive `platform_run_modal_until(bool*)` (`hosts/crossplatform/platform_{win32.cpp,macos.mm}`); win32 native has its own `run_modal_until(bool*)` in `hosts/win32/window.cpp` (re-using `dispatch_one_message` so accelerators + `IsDialogMessage` keep working); macOS native + xpl macOS share `neui_detail::run_modal_pump_macos` in `hosts/shared/macos/modal_pump_macos.h` (`[NSApp nextEventMatchingMask:]` loop). Each host stores a `modal_pump_active` bool on the dialog widget; the dialog's destroy path (WM_DESTROY / `windowWillClose:` / Linux `platform_destroy_window`) clears it so the pump unwinds. **Owner input-block**: win32 `EnableWindow(owner, FALSE)`, macOS the OS sheet; Linux has no native per-window disable, so `platform_set_window_enabled` flags the owner `LinuxWindow.input_disabled` and `dispatch_x_event` swallows all input (button / motion / key + XI2 scroll) bound for it while a modal child is up - a click on the disabled owner raises + focuses the modal dialog; owned dialogs are also marked `_NET_WM_STATE_MODAL`. `platform_destroy_window` re-enables + raises the owner before the dialog widget is freed. Clients dismiss dialogs via `widgets->destroy(dlg)` from their OK / Cancel handler the same as before; `show` simply doesn't return until then. macOS dialogs still use `beginSheet:completionHandler:` for the sheet animation - the pump runs concurrently. `NEUI_ATTR_MODAL=0` keeps the legacy non-blocking shape (owner not disabled, `show` returns immediately).

## Toasts and message boxes (`NEUI_API_NOTIFY`)

`neui_notify_api_t` (`include/neui/d/notify.h`) - user notification surfaces rendered by the host outside the widget tree (no handle, no tree slot, no attrs/events; `parent_window` is an anchor/owner only, must be APPWINDOW / PLUGWINDOW / DIALOG).

**`notify->toast(sess, frame, text)`** - transient notification anchored to the frame's client-area top, centered; `\n` separates display lines, widest line sizes the box (clamped to 70% of the frame width). Self-dismisses after ~2 s; a click on it jumps to the fade-out; a second call replaces the in-flight toast. Per-host feel: xpl paints it as the topmost overlay in the frame's paint pass (`Session::toast_show` / `paint_toast` / `handle_toast_click` in `host.cpp`, `ToastState` on `FrameWidget`, 16 ms heartbeat via `platform_start/stop_toast_animation` + `platform_now_ms`); the xpl anchor + fly-in are computed against `Session::widget_client_rect` (so on the Linux in-frame-menubar host the toast sits *below* the band and is clipped to the content area, not painted over the menubar); win32 native is a layered `WS_POPUP` (32-bpp DIB + `UpdateLayeredWindow`, snappy fly-in / slow fade-out, `hosts/shared/win32/toast_win32.h`, state via `GWLP_USERDATA`, replace via owner-walk `FindWindowExW`); macOS native is a borderless child `NSWindow` with rounded corners + shadow (`hosts/shared/macos/toast_macos.h`, strong ref parked on the parent via `objc_setAssociatedObject`, `@implementation` gated by `NEUI_TOAST_MACOS_IMPLEMENTATION` - widgets.mm emits it).

**`notify->message_box(sess, frame, text, caption, flags) -> int`** - modal, MessageBoxEx-shaped. `NEUI_MB_*` flags (button set / icon / default button) and `NEUI_ID_*` returns match Win32 `MB_*` / `ID*` numerically (same convention as `neui_dnd_action_t` == `DROPEFFECT_*`), so both win32 hosts sanitize-mask and pass straight through to `MessageBoxExW` with `MAKELANGID(LANG_NEUTRAL, SUBLANG_NEUTRAL)` (buttons come out in the user's OS language). macOS hosts share `neui_detail::message_box_macos` (`hosts/shared/macos/message_box_macos.h`): NSAlert run modally, buttons added in Win32 visual order (first-added lands rightmost = macOS idiom; `NSAlertFirstButtonReturn + i` maps back trivially), icon bits -> `NSAlertStyle` **plus** a tinted SF-Symbol set on `alert.icon` (`message_box_icon_macos`: ERROR -> red `xmark.octagon.fill`, QUESTION -> blue `questionmark.circle.fill`, WARNING -> yellow `exclamationmark.triangle.fill`, INFORMATION -> blue `info.circle.fill`; no icon bits -> default app icon). A deliberate divergence from native macOS (NSAlert normally always shows the app icon) so the four Win32 icon classes read distinctly; macOS 11+ via `imageWithSystemSymbolName`, older falls back to the app icon. DEFBUTTON2/3 move the `\r` key equivalent. xpl routes through the `platform_message_box` seam (win32 = `MessageBoxExW`, macOS = the shared helper, null = 0). Returns 0 on failure (bad widget, cross-session, null platform). Blocks like a modal DIALOG; owner disabled by the OS.

## Checkable menu items

`tree->set_checked(menubar, item, bool)` / `get_checked(...)` toggle a checkmark on a leaf menu item. The client owns the logical on/off state - flip it from the item's `NEUI_EVENT_TREE_ITEM_ACTIVATED` handler and call `set_checked` with the new value. A checkmark and a submenu disclosure are mutually exclusive, so top-level popups, submenu parents, and separators ignore it. Per host: Win32 `CheckMenuItem(MF_CHECKED)` (native + xpl; re-asserted on `WM_INITMENUPOPUP` so it survives a menu rebuild); macOS `NSMenuItem.state = NSControlStateValueOn` (native + xpl seam); iOS `UIMenuElementStateOn` on the UIAction/UIKeyCommand (rebuilt from the model on refresh); Linux in-frame menu draws a U+2713 glyph in a left gutter that the column reserves only when one of its rows is checked (so unchecked columns keep their tight layout). Treeview ignores it.

## Keyboard shortcuts and accelerators

`tree->set_shortcut(menubar, item, modifiers, key)` (`NEUI_KMOD_*` bits + `NEUI_KEY_*`). `NEUI_KEY_NONE` clears. Display formatted by `shortcut_format.h`, appended after `\t`. Win32 builds an HACCEL (`accel_table_win32.h`), walked from the pump via `try_translate_accel(MSG*)` before `TranslateMessage` (and before `IsDialogMessage` on xpl). macOS sets `NSMenuItem.keyEquivalent` + `keyEquivalentModifierMask`. `NEUI_KMOD_CTRL` = platform-primary (Cmd on macOS, Ctrl on Win/Linux); `NEUI_KMOD_META` = secondary (Control on macOS).
