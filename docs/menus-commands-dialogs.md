## Routed commands

`NEUI_API_COMMANDS`. `neui_command_t`: `NONE/UNDO/REDO/CUT/COPY/PASTE/SELECT_ALL/DELETE`, `USER_BASE = 0x10000`. API: `invoke_focused(cmd) → bool`, `invoke(widget, cmd) → bool`. `tree->set_menu_cmd(menubar, item, cmd)` binds a menu item to a built-in command. On activation, `dispatch_menu_event` calls `invoke_focused_command(cmd)` first; if a focused widget consumes it, no `TREE_ITEM_ACTIVATED` fires (otherwise, or `cmd == 0` / `cmd >= USER_BASE`, the event reaches the client). `WidgetData::perform_command(cmd)` is the virtual seam; xpl text widgets route to `on_keydown` with a synthetic Ctrl+letter; macOS native (`invoke_focused_command_macos`) routes to the first responder via AppKit editing actions + `NSUndoManager` for UNDO/REDO.

Menu-item auto-disable on popup-open: built-in commands gray via `WidgetData::can_perform_command`; optional `neui_menu_client_t` (`NEUI_API_MENU_CLIENT`) `validate(token, menubar, item, cmd)` per non-separator item. Final `enabled = mi.enabled && (no built-in OR can_focused) && (no validate OR validate())`.

## Popup menus

`widgets->popup_menu(session, anchor, x, y, items[])` - blocking; items NULL-terminated UTF-8 (`"-"` = separator); returns 1-based pick or 0. Win32: `TrackPopupMenuEx` + `TPM_RETURNCMD`. macOS: `run_popup_menu_macos` (`NSMenu`, per-item target; separators consume an index). xpl: session overlay + nested pump via `platform_run_modal_until(bool*)`. Used by the KNOB right-click "Reset to default" menu (`NEUI_EVENT_MOUSE_RBUTTON_DOWN`).

### Rich (tree-model) popup menus - `NEUI_W_POPUPMENU` + `popup_tree_menu`

`widgets->popup_tree_menu(session, anchor, x, y, menu)` shows a `NEUI_W_POPUPMENU` as a context menu. The menu is built with the **same `NEUI_API_TREE` calls as a `NEUI_W_MENUBAR`** (`add` / `remove` / `clear` / `set_text` / `set_enabled` / `set_checked` / `set_shortcut` / `set_menu_cmd`), so submenus to arbitrary depth, per-item enable/disable, checkmarks, shortcut labels, built-in command routing and `NEUI_API_MENU_CLIENT::validate` all work - none of which `popup_menu`'s flat `const char* const*` can express. **xpl host only**, and only where that host routes input to the popup - `platform_supports_tree_popup()`: true on win32 / macOS / Linux, **false on iOS**, where the touch path has no tree-popup hit-test, so `show_tree_popup` refuses rather than painting a cascade that taps fall through and nothing can dismiss (there is no Esc). The native win32 / macOS / iOS hosts hold an explicit `nullptr` in the vtable slot. The shortcut *label* is platform-styled (`format_shortcut_label` - Cocoa glyphs on macOS, `Ctrl+`/`Alt+`/`Shift+` elsewhere), because the popup is the first surface neui draws it on itself: the native `NSMenu` path strips it (`macos_menu_title_only`) and shows `keyEquivalent` instead.

**Asynchronous**, unlike `popup_menu`: returns true once the menu is up, and the pick arrives as **exactly one** `NEUI_EVENT_ITEM_SELECTED` on the *menu* widget with `.index` = the `neui_item_t` id. No `TREE_ITEM_ACTIVATED` (that stays the menu bar's event), so a popup pick is never ambiguous with a menu-bar pick. A row bound to a **built-in** command (`< NEUI_CMD_USER_BASE`) is offered to the focused widget first via `invoke_focused_command`, then `ITEM_SELECTED` fires anyway; USER-range bindings do nothing here - handle those from `ITEM_SELECTED`. A blocking variant was rejected: a nested pump suppresses `NEUI_EVENT_TIMER` for its duration and re-enters the client from inside its own handler. Refuses to open (returns false) on a non-POPUPMENU widget, a cross-session handle, an anchor with no frame, or an **empty** menu.

Implementation: almost entirely reuse, and the reuse point is one branch. `mb_build_columns` already did row sizing, arbitrary-depth cascade placement, right/bottom clamping, the submenu left-flip, checkmark gutters, shortcut columns and validate-driven enabling - all origin-agnostic - so an **empty `band`** now means "standalone popup: level 0 opens at `(root_x, root_y)`" and the column painter was extracted from `paint_menubar` as `paint_menu_columns`, shared verbatim. `Session::show_tree_popup` / `close_tree_popup` / `paint_tree_popup` / `handle_tree_popup_click` / `_hover` / `_key` in `host.cpp`; state in `_tree_popup_*`, borrowing `_menu_path` / `_menu_hover_item` so only one cascade is ever open (true of the OS menus it mirrors).

**Two predicates, not one** - this is the part to get right. `WidgetData::is_menubar()` means "this widget IS its frame's menu bar" and is true for `MENUBAR` only; `is_menu_model()` means "this widget stores the `MenubarWidget` item model" and is true for both. The tree API dispatches on `is_menu_model()` (it `dynamic_cast`s to `MenubarWidget&`), as do the layout / paint / hit-test / tab walks; everything that makes a widget a menu *bar* keys off `is_menubar()` - the native `HMENU` / `NSMenu` created at `widget_create`, `SetMenu` / `[NSApp setMainMenu:]` at `widget_show`, the reserved Linux band, `frame_menubar_index`, and registration in `Session::_menubars`. A third predicate, `MenubarWidget::uses_native_menu()` (true for MENUBAR, false for POPUPMENU), gates the `platform_menubar_*` calls inside the tree API: a popup keeps the item model and owns no native menu. Getting this wrong is not cosmetic - a POPUPMENU that answers yes to `is_menubar()` **replaces the app's real menu bar on `show()`**, which is exactly what the first version of this feature did.

Consequences that follow from the above and are worth knowing: a popup's root children are **ordinary rows** (a menu bar's root children are top-level titles), so they get command ids, honour `"-"` as a separator, and are pickable; a popup is absent from `_menubars`, so its per-item shortcuts are **labels only** - nothing translates them into accelerators, so bind the real accelerator on the menu bar; and its command ids restart at `0x8000` like every menu widget's, which is why a pick must never be routed through `dispatch_menu_event`'s `_menubars` scan (that would hand the pick to whichever menu bar holds the same id).

Teardown: `widget_destroy` calls `close_tree_popup_if_within` **before** the subtree goes away, `tp_claim` self-heals if the cascade can no longer be built, `tree->clear` closes an open popup itself (an emptied model still builds one zero-row column, so `tp_build` does *not* catch that case), Linux `FocusOut` closes it explicitly (`close_menubar_menu` alone would clear the borrowed `_menu_path` and leave `_tree_popup_active` set), and every platform hook honours the handler's `bool` return - input on another frame dismisses the popup *without* consuming the click. A consumed press arms `Session::tree_popup_take_release`, drained by each platform's button-up path so the widget under a dismissed menu never sees an UP without a DOWN; every button-DOWN path first calls `tree_popup_discard_pending_release()`, so an armed flag can never outlive its own gesture (on win32 a consumed press takes no capture, so releasing outside the window delivers no `WM_LBUTTONUP` at all, and the stale flag would have eaten the next click's UP - leaving `_pressed_widget` stuck and, on a KNOB / SLIDER, a `GESTURE_BEGIN` with no `GESTURE_END`). The wheel is absorbed while a popup is open on all three platforms. Verified by `tests/popup_tree_smoke_macos.mm` (41 checks, each negative-probed).

## Modal dialogs

`widgets->show(sess, dialog)` blocks the calling thread until the modal DIALOG (`NEUI_ATTR_MODAL=1`, default) is destroyed. All three hosts run a nested OS event pump while modal: xpl reuses the popup-menu primitive `platform_run_modal_until(bool*)` (`hosts/crossplatform/platform_{win32.cpp,macos.mm}`); win32 native has its own `run_modal_until(bool*)` in `hosts/win32/window.cpp` (re-using `dispatch_one_message` so accelerators + `IsDialogMessage` keep working); macOS native + xpl macOS share `neui_detail::run_modal_pump_macos` in `hosts/shared/macos/modal_pump_macos.h` (`[NSApp nextEventMatchingMask:]` loop). Each host stores a modal-pump flag on the dialog widget; the dialog's destroy path (WM_DESTROY / `windowWillClose:` / Linux `platform_destroy_window`) clears it so the pump unwinds. **On the xpl host that flag is a `std::shared_ptr<bool>` (`FrameWidget::modal_pump_flag`), and the indirection is load-bearing rather than a style choice**: the documented way out of a modal dialog is for a client callback to `destroy()` the dialog *widget*, which frees the `WidgetData` while the pump is still polling, so a plain `bool` member meant the poll read freed memory and whether the loop exited came down to what the allocator left in the byte - it survived by luck on the client-destroy path and hung outright when the destroy arrived from a callback dispatched during the dialog's own `WM_DESTROY`. `widget_show` keeps a share alive across the pump (found by `tests/focus_smoke_win32.cpp`, 2026-08-11; the defect was in portable code, so all three xpl platforms had it). **Both NATIVE hosts carry the same fix as of 2026-08-13** (`WidgetData::modal_pump_flag`, `hosts/win32/host.h` + `hosts/macos/host.h`) - they previously passed `&w.modal_pump_active`, a pointer into the `Tree<WidgetData>` slot, and had the identical use-after-free. macOS is verified by `tests/modal_smoke_macos.mm` (both hosts, under Guard Malloc so a read of freed memory faults rather than usually working); win32 is compile-only from the macOS side, with `tests/focus_smoke_win32.cpp` as the harness to re-run there. **One modal defect remains open on the native macOS host: the THIRD sequential modal dialog never unwinds** - pre-existing, unrelated to this fix, with a repro command in `docs/deferred-issues.md`. **Owner input-block**: win32 `EnableWindow(owner, FALSE)`, macOS the OS sheet; Linux has no native per-window disable, so `platform_set_window_enabled` flags the owner `LinuxWindow.input_disabled` and `dispatch_x_event` swallows all input (button / motion / key + XI2 scroll) bound for it while a modal child is up - a click on the disabled owner raises + focuses the modal dialog; owned dialogs are also marked `_NET_WM_STATE_MODAL`. `platform_destroy_window` re-enables + raises the owner before the dialog widget is freed. Clients dismiss dialogs via `widgets->destroy(dlg)` from their OK / Cancel handler the same as before; `show` simply doesn't return until then. macOS dialogs still use `beginSheet:completionHandler:` for the sheet animation - the pump runs concurrently. `NEUI_ATTR_MODAL=0` keeps the legacy non-blocking shape (owner not disabled, `show` returns immediately).

## Toasts and message boxes (`NEUI_API_NOTIFY`)

`neui_notify_api_t` (`include/neui/d/notify.h`) - user notification surfaces rendered by the host outside the widget tree (no handle, no tree slot, no attrs/events; `parent_window` is an anchor/owner only, must be APPWINDOW / PLUGWINDOW / DIALOG).

**`notify->toast(sess, frame, text)`** - transient notification anchored to the frame's client-area top, centered; `\n` separates display lines, widest line sizes the box (clamped to 70% of the frame width). Self-dismisses after ~2 s; a click on it jumps to the fade-out; a second call replaces the in-flight toast. Per-host feel: xpl paints it as the topmost overlay in the frame's paint pass (`Session::toast_show` / `paint_toast` / `handle_toast_click` in `host.cpp`, `ToastState` on `FrameWidget`, 16 ms heartbeat via `platform_start/stop_toast_animation` + `platform_now_ms`); the xpl anchor + fly-in are computed against `Session::widget_client_rect` (so on the Linux in-frame-menubar host the toast sits *below* the band and is clipped to the content area, not painted over the menubar); win32 native is a layered `WS_POPUP` (32-bpp DIB + `UpdateLayeredWindow`, snappy fly-in / slow fade-out, `hosts/shared/win32/toast_win32.h`, state via `GWLP_USERDATA`, replace via owner-walk `FindWindowExW`); macOS native is a borderless child `NSWindow` with rounded corners + shadow (`hosts/shared/macos/toast_macos.h`, strong ref parked on the parent via `objc_setAssociatedObject`, `@implementation` gated by `NEUI_TOAST_MACOS_IMPLEMENTATION` - widgets.mm emits it).

**`notify->message_box(sess, frame, text, caption, flags) -> int`** - modal, MessageBoxEx-shaped. `NEUI_MB_*` flags (button set / icon / default button) and `NEUI_ID_*` returns match Win32 `MB_*` / `ID*` numerically (same convention as `neui_dnd_action_t` == `DROPEFFECT_*`), so both win32 hosts sanitize-mask and pass straight through to `MessageBoxExW` with `MAKELANGID(LANG_NEUTRAL, SUBLANG_NEUTRAL)` (buttons come out in the user's OS language). macOS hosts share `neui_detail::message_box_macos` (`hosts/shared/macos/message_box_macos.h`): NSAlert run modally, buttons added in Win32 visual order (first-added lands rightmost = macOS idiom; `NSAlertFirstButtonReturn + i` maps back trivially), icon bits -> `NSAlertStyle` **plus** a tinted SF-Symbol set on `alert.icon` (`message_box_icon_macos`: ERROR -> red `xmark.octagon.fill`, QUESTION -> blue `questionmark.circle.fill`, WARNING -> yellow `exclamationmark.triangle.fill`, INFORMATION -> blue `info.circle.fill`; no icon bits -> default app icon). A deliberate divergence from native macOS (NSAlert normally always shows the app icon) so the four Win32 icon classes read distinctly; macOS 11+ via `imageWithSystemSymbolName`, older falls back to the app icon. DEFBUTTON2/3 move the `\r` key equivalent. xpl routes through the `platform_message_box` seam (win32 = `MessageBoxExW`, macOS = the shared helper, null = 0). Returns 0 on failure (bad widget, cross-session, null platform). Blocks like a modal DIALOG; owner disabled by the OS.

### File dialogs (`open_file` / `save_file`)

Appended to `neui_notify_api_t` (so a client **must null-check the slots** before calling - the vtable-append rule). Both are modal and blocking, same contract as `message_box`, and both deliver results through a per-path callback rather than an out-parameter: no allocation ownership question, no size-query round trip (impossible for an interactive dialog), and multi-select falls out for free.

```c
neui_file_filter_t f[] = { { "Presets", "*.preset" }, { "All files", "*" } };
neui_file_dialog_t d = {0};                 // zero-init; every field optional
d.title = "Load preset"; d.filters = f; d.filter_count = 2;
int n = notify->open_file(sess, frame, &d, on_path, &ctx);
```

**Return values.** `N>0` = that many callbacks fired, `0` = the user cancelled (or, rarely, confirmed a selection the host could not resolve to a filesystem path), **`-1` = no dialog was shown at all** (bad/unrealised/non-frame widget, cross-session handle, or a host with no file-dialog surface). `-1` and `0` are deliberately distinct: a client that wants to fall back to its own path entry must do so only on `-1`, never because someone pressed Cancel. `save_file` returns at most 1. A NULL `cb` is legal (the dialog runs, the count is still returned) but discards the choice - feature-detect on the slot, not by calling.

**Descriptor.** `title` / `initial_dir` / `initial_name` (save only) / `filters` + `filter_count` / `default_filter` (clamps to 0 when out of range) / `flags`. A NULL descriptor means "every default". Flags: `NEUI_FD_MULTISELECT` (open only), `NEUI_FD_DIRECTORY` (pick a folder; open only, filters ignored), `NEUI_FD_NO_OVERWRITE_PROMPT` (save only; the prompt is **on** by default), `NEUI_FD_SHOW_HIDDEN` (a hint - native dialogs may let the user's own shell setting win).

**Filters** are semicolon-separated glob lists (`"*.png;*.PNG"`). Only `*` and `?` are special, and matching is ASCII **case-insensitive on every platform** - a deliberate divergence from the case-sensitive filesystem, matching what users expect of a type filter. `"*"` / `"*.*"` is the "every file" escape hatch and is never turned into an extension whitelist.

**Save completion rule.** A typed name with no extension gains the active filter's (`"lead"` + `Presets (*.preset)` -> `lead.preset`). A name that already has one is left alone **even if it does not match the filter** - second-guessing a deliberate `.txt` is worse than obeying the user. A leading dot does not count as an extension (`.bashrc` is a hidden file, not `bashrc` of type `rc`).

**Portable model.** `hosts/shared/file_dialog_model.h` owns everything that is easy to get subtly wrong - `glob_match`, `parse_filters`, `clamp_default_filter`, `complete_extension`, `path_join` / `path_parent` / `path_leaf`, `list_directory_view` - and is Tier-1 tested (`tests/test_file_dialog_model.cpp`). It is used by all three real platforms, not just the drawn fallback: it feeds `COMDLG_FILTERSPEC`, `allowedContentTypes`, and the portal's `a(sa(us))`. Two invariants worth knowing: a type filter **never hides directories** (you have to navigate into a folder to reach the files in it), and the listing sort is a *total* order over case variants (an unstable comparator would reorder rows between reads).

**Per host.**
- **win32** (native + xpl, `hosts/shared/win32/file_dialog_win32.h`): `IFileOpenDialog` / `IFileSaveDialog`. Patterns pass through to `SetFileTypes` verbatim, so `*.p?g` still works here. `SetFileTypeIndex` is **one-based** - the zero-based `clamp_default_filter` result is `+1`'d. `SetDefaultExtension` implements the completion rule for the default filter, and because it is a pre-`Show` call that a `"*"` default leaves unset, the save path *also* reads `GetFileTypeIndex` afterwards and completes against whichever filter was actually active; `FOS_OVERWRITEPROMPT` is default-on for save, `FOS_PICKFOLDERS` for `NEUI_FD_DIRECTORY`, `FOS_FORCEFILESYSTEM` so a search result or library never comes back as a path the client cannot open. `NEUI_FD_SHOW_HIDDEN` is a no-op (the shell has no per-dialog switch). Needs `ole32` + `shell32`, added to both hosts' link lines.
- **macOS** (native + xpl, `hosts/shared/macos/file_dialog_macos.h`): `NSOpenPanel` / `NSSavePanel` run modally (app-modal, so the owner window is validation only, not a required sheet parent). Filters map to `allowedContentTypes` (`UTType`) rather than the deprecated `allowedFileTypes`, which costs two things: an extension-internal wildcard (`*.p?g`) cannot be expressed and is dropped, and an all-files filter leaves `allowedContentTypes` **unset** rather than empty (an empty array means "allow nothing" and greys out every file). macOS 11+; older systems simply do not filter by type. `NEUI_FD_NO_OVERWRITE_PROMPT` is a no-op - NSSavePanel always confirms and offers no switch, which is the safe direction to diverge in.
- **Linux** (xpl only): the **XDG desktop portal** (`org.freedesktop.portal.FileChooser`, `hosts/shared/linux/file_dialog_portal.h`) first, then a **neui-drawn browser** (`run_file_browser` in `platform_linux.cpp`) as the fallback - the same graceful-degradation shape as the message box. Details below.

**The Linux fall-through is deliberately narrow.** `file_dialog_portal` returns a tri-state, not a count: `unavailable` (no libdbus at build time, no session bus, no portal installed, a malformed reply, a timeout) runs the drawn browser; `cancelled` does **not** - the portal already put a chooser on screen, so a second dialog on top of a dismissed first is worse than having no portal path at all. The portal is asynchronous (a method call returns a Request object path, the answer arrives as a `Response` signal on it), so the implementation passes its own `handle_token` and precomputes the path, installing the match rule *before* the call goes out; a portal old enough to ignore the token returns a different handle, which is detected and falls through rather than hanging. The connection is private (`dbus_bus_get_private`) so it cannot collide with the theme tracker's filter on the shared bus, and a pump callback keeps the app's own windows repainting while the chooser is up.

**The drawn browser** is the no-desktop fallback, not a file manager: fixed 560x420, path bar + Up, a scrolling list (wheel / arrows / PageUp-Down, no draggable thumb), a name field for save (backed by the shared `TextEditState`, so word nav and Delete/Home/End work), a filter chip that **cycles** the type list on click, and OK / Cancel. Double-click or Enter enters a directory; Enter on a file confirms; Backspace goes up a level in open mode; Ctrl-H toggles hidden files; Ctrl-click marks rows under `NEUI_FD_MULTISELECT`. Folder mode with nothing selected picks the folder currently open - without that, a directory with no subdirectories is a dead end where OK never enables. Saving over an existing file raises an in-window overwrite confirmation (unless `NEUI_FD_NO_OVERWRITE_PROMPT`): a scrim plus a panel whose *default* answer on both Enter and Esc is the non-destructive one, absorbing the wheel while it is up. It is drawn in-window rather than nesting `run_message_box`, because that helper disables a `LinuxWindow*` owner and the browser's X window is not one - a nested box would leave the browser clickable underneath.

**Not on iOS.** Both slots return `-1`. `UIDocumentPickerViewController` is presented, not run modally - the same asynchrony behind the `message_box` divergence above, but with no useful sentinel available, because the return value *is* the path list and a client told "pending" could not proceed. Declining is better than showing a picker whose result is dropped. The async completion event that would fix both is tracked in `docs/deferred-issues.md`.

## Checkable menu items

`tree->set_checked(menubar, item, bool)` / `get_checked(...)` toggle a checkmark on a leaf menu item. The client owns the logical on/off state - flip it from the item's `NEUI_EVENT_TREE_ITEM_ACTIVATED` handler and call `set_checked` with the new value. A checkmark and a submenu disclosure are mutually exclusive, so top-level popups, submenu parents, and separators ignore it. Per host: Win32 `CheckMenuItem(MF_CHECKED)` (native + xpl; re-asserted on `WM_INITMENUPOPUP` so it survives a menu rebuild); macOS `NSMenuItem.state = NSControlStateValueOn` (native + xpl seam); iOS `UIMenuElementStateOn` on the UIAction/UIKeyCommand (rebuilt from the model on refresh); Linux in-frame menu draws a U+2713 glyph in a left gutter that the column reserves only when one of its rows is checked (so unchecked columns keep their tight layout). Treeview ignores it.

## Keyboard shortcuts and accelerators

`tree->set_shortcut(menubar, item, modifiers, key)` (`NEUI_KMOD_*` bits + `NEUI_KEY_*`). `NEUI_KEY_NONE` clears. Display formatted by `shortcut_format.h`, appended after `\t`. Win32 builds an HACCEL (`accel_table_win32.h`), walked from the pump via `try_translate_accel(MSG*)` before `TranslateMessage` (and before `IsDialogMessage` on xpl). macOS sets `NSMenuItem.keyEquivalent` + `keyEquivalentModifierMask`. `NEUI_KMOD_CTRL` = platform-primary (Cmd on macOS, Ctrl on Win/Linux); `NEUI_KMOD_META` = secondary (Control on macOS).
